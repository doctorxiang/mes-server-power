01技术链路总图

一句话：浏览器里跑的是 Vue 单页应用（SPA），它只跟后端说话（HTTP + JSON）；后端是 ASP.NET Core 分层服务，数据落在 MySQL；Redis/RabbitMQ/MinIO 是可选中间件，缺了会自动降级，不影响跑通。

给 C# 程序员的映射：Vue 组件 ≈ WinForms/WPF 的 UserControl；Pinia ≈ 全局单例服务；Vue Router ≈ 前端自己的"页面地址表"；Axios ≈ HttpClient 封装；EF Core 你本来就熟；JWT ≈ 自带的 Forms 认证换成无状态 token。

这是全系统最核心的接口：POST /api/production/scan。跟着一个 SN 走一遍，整条链路就通了。

03前端链路：你要补的 Vue 课（按这个顺序学）

文件/概念干什么用C# 里的对应物
index.html → main.ts入口：创建 app，装 Pinia、Router，挂到 #appProgram.cs
router/index.ts路径 → 页面组件的映射表；beforeEach 守卫做登录/角色拦截路由注册 + 授权过滤器
stores/*.tsPinia 全局状态：auth（token/角色）、tabs（页签）。组件里 useAuthStore() 直接读写单例 Service + 内存状态
api/client.tsAxios 实例：baseURL=/api，请求头自动塞 JWT，401 自动刷新 token，错误统一转文案DelegatingHandler
api/mes.ts按模块分组的接口清单，页面只调这些函数，不直接碰 axios强类型的 Client 接口
views/*.vue页面。<script setup> 写状态和函数，<template> 写模板，<style> 写样式一个 Page 类
components/跨页面复用的组件（AppShell 骨架、NavIcon 图标）自定义控件
types.ts和后端 Contracts 一一对应的 TypeScript 接口DTO / Contracts

必须建立的三个心智模型

1
响应式 = 状态变了 UI 自动变。 ref() 包住的变量一改，模板里用到它的地方自动重渲染。不需要手动刷新控件。
2
单向数据流。 父组件用 props 传数据下去，子组件用 emit 传事件上来。数据永远从上往下。
3
一切异步。 后端调用全是 async/await（和 C# 一样），配合 loading 状态变量控制按钮转圈。
热更新（HMR）：dev 模式下 Vite 用 WebSocket 盯着文件，改了 .vue 只替换那个模块、保留页面状态，不用刷新浏览器。后端对应物是 dotnet watch（热重载方法体）。

04后端链路：你的主场（项目做了哪些约定）

层约定
Controllers薄：只做鉴权（[Authorize(Roles=...)]）、参数绑定、调 Service、包返回值。不写业务。
Services业务全在这。接口 + 实现注册到 DI（builder.Services.AddScoped<IX, X>()）。业务报错抛 AppException(message, statusCode)，全局中间件统一转 JSON。
DomainEF Core 实体（WorkOrder / SerialUnit / SnMoveLog / RepairRecord / QcInspection…17 张表）。
ContractsAPI 出入参 record。返回给前端的形状只在这里定义。
DataMesDbContext + Migrations。改实体后 dotnet ef migrations add Xxx（注意设 Database__Provider=MySql，否则会生成 SQLite 方言）。
Infrastructure缓存（Redis→内存降级）、文件存储（MinIO→本地磁盘）、审计过滤器、全局异常处理、JWT 发放。

EF Core 三个坑（本项目踩过的）

  • AsNoTracking 查出来的导航实体再 SaveChanges 会被当成新记录插入（UNIQUE 冲突）。跨上下文带实体只用 Id，重新 db.Set<T>().Find(id)。
  • 没有导航属性的关联要先 SaveChanges 拿到 Id（如 SnMoveLog 记 WorkOrderId）。
  • SQLite EnsureCreated 不会给已有表加列——演示库改结构要么删库重跑，要么手写 ALTER TABLE。

06本地跑起来（第一次 10 分钟）

1
起中间件（可选）。 装了 Docker 就 docker compose up -d，MySQL/Redis/RabbitMQ/MinIO 全起；没装也能跑——后端会降级成 SQLite + 内存缓存 + 本地磁盘。
2
起后端。 cd backend/MesApi && dotnet run，监听 :5080。首次启动自动建库 + 种子数据 + 演示工单。
常用参数：--topup-demo 补演示数据、--reset-demo 重置生产数据。
3
起前端。 cd frontend && npm install && npm run dev，打开 http://localhost:5173。
4
登录。 演示账号：admin / Admin@12345（管理员）、leader / Leader@123（班组长）、qc1 / Qc@123（质检）、op1 / Op@123（操作工）。
5
验证。 bash backend/test-api.sh 跑接口冒烟；node .e2e/e2e.mjs 等跑浏览器回归。

07部署到服务器（两种方式，选一种）

方式 A：裸机部署（理解原理首选）

1
发后端。 开发机执行 dotnet publish backend/MesApi -c Release -o publish/api；把 publish/api 拷到服务器 /opt/mes/api。
2
systemd 守护。 建 /etc/systemd/system/mes-api.service：
[Unit]
Description=MES API
After=network.target mysql.service

[Service]
WorkingDirectory=/opt/mes/api
ExecStart=/usr/bin/dotnet /opt/mes/api/MesApi.dll
Environment=ASPNETCORE_URLS=http://localhost:5080
Environment=Database__Provider=MySql
Environment=ConnectionStrings__MySql=Server=localhost;Database=mes;User=mes;Password=***;
Restart=always
User=mes

[Install]
WantedBy=multi-user.target

然后 sudo systemctl enable --now mes-api。改配置用环境变量覆盖 appsettings（配置节__子键 命名）。

3
发前端。 cd frontend && npm run build，产物 dist/ 拷到 /opt/mes/web。
4
Nginx 站点（静态 + 反代一个域名搞定，前端不用跨域）：
server {
    listen 80;
    server_name mes.example.com;

    # 前端 SPA：找不到路径就回 index.html
    root /opt/mes/web;
    index index.html;
    location / { try_files $uri $uri/ /index.html; }

    # 后端 API 与 SignalR
    location /api  { proxy_pass http://127.0.0.1:5080; proxy_set_header Host $host; }
    location /hubs { proxy_pass http://127.0.0.1:5080; proxy_http_version 1.1;
                     proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade"; }
}
上 HTTPS：证书放好后再 listen 443 ssl，扫码枪混 HTTP 会有 Mixed Content 报错。内网先 HTTP 跑通再补证书。

方式 B：Docker Compose

仓库里的 docker-compose.yml 已包含 mysql / redis / rabbitmq / minio / adminer；后端补一个 Dockerfile（多阶段：SDK build → aspnet runtime），生产 compose 加上 api 服务即可。docker compose up -d --build 一条命令起全套。

数据库迁移上线顺序

1
停旧版 → 备份数据库（mysqldump）
2
发新版，启动时执行 dotnet ef database update（或保持项目现有的启动自动迁移逻辑）
3
跑一遍 test-api.sh 冒烟再放行车间流量

08上传 GitHub + 让别人能访问网页

第一步：把项目推上去（本地仓库已就绪，123 个文件，.gitignore 已挡住 node_modules/数据库/截图）

# 1. 在 GitHub 网页上新建一个空仓库（不要勾选 README），例如 mes-server-power
git remote add origin https://github.com/<你的用户名>/mes-server-power.git
git branch -M main
git push -u origin main

# 以后每次：git add -A && git commit -m "..." && git push
推送前检查：appsettings.json / docker-compose.yml 里的真实密码改成占位符（*** 或环境变量），仓库是公开的话谁都能看到。建议用 dotnet user-secrets 或环境变量注入。

第二步：GitHub Pages —— 能做什么、不能做什么

结论说明
能做Pages 是免费静态网站托管：把 frontend/dist 发上去，任何人都能打开 https://<用户名>.github.io/mes-server-power/ 看到登录页和界面布局。
不能做Pages 跑不了 ASP.NET 后端和 MySQL，它只发静态文件。所以别人打开网页后，登录/过站这些接口调用会失败——除非接口另有部署地址。

所以「GitHub 帮我形成网站」的正确姿势是三选一：

  • 只展示界面（零成本，10 分钟）：用我加的 .github/workflows/deploy-frontend.yml，推送到 main 自动构建前端并发布到 Pages。仓库 Settings → Pages → Source 选 GitHub Actions 即生效。访客能看 UI，功能要等你把后端也部署了才能用。
  • 完整可用的演示站：后端 + MySQL 部署到一台便宜云服务器（阿里云/腾讯云轻量 ~30 元/月）或 Render/Railway 免费层，然后前端构建时把 client.ts 的 baseURL 指到 https://api.你的域名（记得后端 CORS 允许 github.io 域名）。Pages 管前端，服务器管接口。
  • 内网真实使用：按第 7 节部署到车间服务器，跟 GitHub 无关；GitHub 只当代码仓库和文档站。

Pages 工作流已就绪

我已加好 .github/workflows/deploy-frontend.yml：推送 main 自动 npm run build -- --base=./（相对路径，适配 github.io/仓库名/ 子路径），并把 index.html 复制成 404.html 兜底 SPA 深链接。合并后去 Settings → Pages 确认 Source 是 GitHub Actions，第一次跑完就能访问。

验证顺序：push → 仓库 Actions 页看绿色对勾 → Settings/Pages 出现访问地址 → 打开看到登录页即成功。想让访客看到"活的"系统，就再按第 7 节把后端架起来，改一行 baseURL 重新 build。
